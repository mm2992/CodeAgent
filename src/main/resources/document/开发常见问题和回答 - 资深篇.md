# 开发常见问题与解决方案 · 资深篇


#### 问题 1：团队技术栈混乱，微服务拆分过细导致运维成本飙升，如何治理？

**答**：  
这是典型的“过度微服务”症状。治理策略：  
- **划定核心域与非核心域**：核心业务保持高内聚，非核心可合并或回归单体模块。  
- **制定服务划分原则**：以业务能力（Bounded Context）而非数据表为边界，避免分布式事务泛滥。  
- **引入 API 网关与服务模板**：统一脚手架（Spring Boot Starter）规范日志、监控、鉴权。  
- **定期进行架构健康度评审**，以“交付效率”和“故障恢复时间”作为度量指标，果断合并低频变更的服务。

#### 问题 2：线上故障复盘时，发现监控告警滞后且缺少业务视角，如何改进？

**答**：  
从三个维度升级：  
1. **指标层**：除基础（CPU/内存）外，增加业务黄金指标（请求量、错误率、响应时间、饱和度），并设置多级阈值。  
2. **链路层**：全链路追踪（如 SkyWalking）结合业务标签（订单号、用户等级），便于快速关联业务影响。  
3. **告警治理**：减少“噪音告警”，引入告警分级（P0/P1/P2）和值班轮换，同时建立“告警-工单-根因分析”闭环。  
建议每月组织一次“故障演练”，检验监控有效性。

#### 问题 3：数据库选型纠结于 MySQL 还是 PostgreSQL，作为负责人如何决策？

**答**：  
不迷信“最好”，而是结合团队能力和业务场景：  
- **选 MySQL**：如果业务以事务性 OLTP 为主、团队对 MySQL 运维经验丰富、且需要大量第三方工具（如 Percona）。  
- **选 PostgreSQL**：如果涉及地理空间、复杂 JSON 操作、自定义函数，或需要更高的 SQL 标准兼容性。  
- **关键决策点**：评估迁移成本、备份恢复工具、扩容方案（如分库分表中间件支持度）。  
建议先做 PoC，压测读写混合场景，并考虑未来 3 年的数据增量。

#### 问题 4：开发团队交付速度慢，需求频繁变更，如何提升研发效能？

**答**：  
效能问题往往不是技术单一因素。措施：  
- **流程侧**：引入敏捷看板，限制 WIP（在制品数量），缩短迭代周期（2 周→1 周），强制需求准入标准（PRD + 交互稿）。  
- **技术侧**：建设 CI/CD 流水线，自动化测试（单元+接口+UI）覆盖核心路径，减少手工回归。  
- **组织侧**：每周固定技术评审会，提前评估技术难点；对重复性需求抽取为配置化能力，减少定制开发。  
度量采用“需求交付周期”和“变更失败率”，而非代码行数。

#### 问题 5：如何向老板说明技术债务的严重性并争取重构资源？

**答**：  
用“业务语言”翻译技术债：  
- 将历史遗留问题转化为“新增需求延迟交付天数”或“线上故障恢复平均时长”。  
- 选取 1～2 个典型“卡脖子”模块（如支付、订单），量化每次变更涉及改动文件数、测试回归耗时。  
- 提出“逐步重构”计划，而非“推倒重来”，绑定业务价值（如支持新渠道接入、提升并发上限）。  
- 请求在每迭代中固定 20% 的人力用于治理，并设立“质量门禁”（如圈复杂度超过 15 禁止合并）。  
获得支持后，务必每季度展示重构带来的故障下降数据。

#### 问题 6：多云/混合云架构下，如何设计容灾与多活方案？

**答**：  
核心思路是“数据同步 + 流量路由 + 故障切换”：  
- **数据层**：采用双向同步（如 DTS）或分布式数据库（如 TiDB），确保 RPO 尽量小。  
- **流量层**：全局 DNS 智能解析，结合 GSLB 按地域或权重分配流量，健康检查探测机房状态。  
- **应用层**：无状态设计，会话共享（Redis 集群跨机房），并实现“单元化”（每个机房独立处理一部分用户）。  
- **演练**：每季度执行“混沌工程”断网演练，验证自动切换时间和数据一致性。  
注意成本与复杂度平衡，通常推荐“同城双活 + 异地灾备”入门方案。
